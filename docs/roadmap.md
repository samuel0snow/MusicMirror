# 后续优化与迁移建议

本次先打通双模块全栈链路，以下不作为当前运行依赖。

| 主题 | 当前方案 | 后续建议 / 迁移时机 |
| --- | --- | --- |
| SQL数据库 | SQLite本地文件、事务、单进程 | 正式多用户部署优先PostgreSQL；需要并发写、多实例或托管备份时迁移。JSON用JSONB、时间用timestamptz，保留快照ID与版本并做回归 |
| MySQL | 未使用 | 已有团队MySQL运维标准时也可选，不同时维护两套生产驱动 |
| ORM / 迁移 | 参数化SQL、初始迁移 | 结构增长后选Prisma/Drizzle或独立迁移工具之一，补升级回滚与旧数据测试 |
| 队列 | SQLite状态+单进程worker | 多实例/并发采集/定时任务时改Redis+BullMQ，统一分布式锁、幂等、死信和取消 |
| 缓存 | SQLite用户加密缓存、公共元数据TTL | 并发升高时Redis热缓存；删除操作覆盖所有存储，不把Cookie放缓存键 |
| 容器化 | npm直接运行 | 环境稳定、CI/CD目标确定后Dockerfile/Compose；API与数据库/Redis分离，挂载数据卷，密钥不进镜像 |
| Kubernetes | 不需要 | 只有服务规模和运维能力有必要时引入，当前不是前置依赖 |
| 真实API | fixture和本地假上游 | 后续测试账号核对字段、权限、速率和版本；保存脱敏fixture后调整适配器 |
| 近期红心自动采集 | 用户指定≤50首及可选时间 | 核实红心歌单排序/时间语义后自动化，不能按likelist顺序猜时间；保留手动入口 |
| 登录 | Cookie校验绑定、演示登录 | GUI阶段二维码授权；正式微信身份接wx.login，生产禁用演示入口 |
| 安全 | AES-GCM、本地密钥、token哈希、TTL | 生产KMS/轮换、TLS、配额、审计、备份与删除时限；密钥迁移须可恢复 |
| 观测 | health、任务状态、安全错误 | 增加脱敏日志、trace、队列深度、上游延迟、失败告警 |
| GUI | wx.request+按钮处理器 | 微信原生双模块主页、对照、解释、历史、分享；null显示数据不足，权重/来源可见 |
| 校准 | 初始阈值、线性描述值 | 真实样本分层百分位、置信度校准；新版本只新增快照 |
| 审美特征 | 歌手/专辑/可靠年代 | 核实曲风/语言/相似艺人后增加；旋律/人声/情绪需要可追溯特征，不由歌名猜 |
| 长期画像 | 双模块对照、三点趋势 | 观察收藏进入长期循环的转化、多窗口偏好变化，不推断人格与心理因果 |

建议顺序：真实接口/近期红心来源验证 → 双模块GUI → 生产认证与数据库/队列迁移 → 容器化/监控 → 校准与审美增强。按真实瓶颈推进，不为目录齐全提前引入设施。
