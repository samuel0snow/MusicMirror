# 歌曲字段补全

## 来源与语义

`design/API 文档.txt`指向Enhanced API在线文档。歌曲百科接口`/song/wiki/info?id=...`在已部署4.40.1中可用，源码位于[上游模块](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/blob/main/module/song_wiki_info.js)。本次按真实响应验证以下路径，仅提取`bizCode=songDetailNewSongWiki`内`rnData.blocks`中`blockCode=wikiSubBlockBaseInfoVo`的基本信息。

| 百科基本信息标题 | 输出字段 | 规则 |
| --- | --- | --- |
| 曲风 | styleIds、styles | 保留标签ID及名称，去重；不混入推荐标签 |
| 语种 | language | 保留上游原值，不根据艺人或歌名猜测 |
| BPM | bpm | 有限、正数且≤400；不读取乐谱演奏版BPM |
| 发行时间 | wikiPublishTime | 严格有效日期且不在未来；与原publishTime分别保留，原值缺失才补入 |
| 推荐标签 | recommendationTags | 独立保存；这是平台标签，不作为心理或音频情绪测量 |

百科由平台及共建信息提供，来源可追溯不代表标签已经由人工音乐学标注验证。百科基本信息发行时间不同于MV发布时间；BPM不同于乐谱BPM。本次探测确实出现171与乐谱170的差异，解析器只取歌曲基本信息。

缺失的歌手、专辑不通过百科文本强行补出ID。未知收藏时间仍为null；百科的首次收听时间也不能代替收藏时间。百科接口还有私人听歌记忆、评论及歌词等，本项目只缓存上述允许字段，不保存完整百科响应。

## 运行与保存

```powershell
# 先启动本地只读桥（已开放song/wiki/info、song/wiki/summary、album读取）
npm start --prefix services/netease-api-enhanced
# 从指定已保存快照补全，只改变元数据
npm run enrich:account -- .data/real-test e7176710-d738-4b85-8230-5e8392518e82
npm run export:account -- .data/real-test
```

输入1与输入2并集逐首查询，500ms最小调度间隔，已有请求超时/有限重试规则。公开字段投影在按用户隔离的加密缓存中保存7天，后续常规采集会复用；空百科记为empty，失败保留原详情并记录warning。缓存过期后可重新执行补全命令；常规采集不自动对全部最近播放歌曲进行百科请求。

命令要求数据库恰好一个真实测试账户、无正在采集的任务、当前输入与源快照相符、源原始响应尚未超过24小时TTL。生成新的不可变快照，不覆盖旧快照。保留原采集时间及所有播放/红心字段，另外记录每首百科查询时间、解析器版本、available/empty状态。补全产生的同日快照不能视为用户审美变化。

CSV新增styles、bpm、wikiPublishTime、recommendationTags、enrichment；JSON schemaVersion升级为2，并附字段覆盖数量。旧快照及其导出保持原始证据，新导出放到新的snapshotId目录，使用新链接查看。

## 收藏顺序与重新收藏语义核验

术语修正：本节“收藏”仅指红心加入“我喜欢的音乐”，与将歌曲加入自订歌单、收藏/订阅整张歌单区分。后续核验称取消/重新点红心；当前输入2不采集自订歌单。

账号持有人确认：时间排序与两首手动调过位置的歌曲的真实收藏时间吻合。因此本账号已验证两个样本的at与收藏时间相符，以及手动排序会使歌单位置偏离收藏时间顺序；不能据此把所有歌曲的at定义为首次收藏时间。

随后只读检查当前歌单：309个不同歌曲ID各一条trackId记录，可识别的毫秒时间字段仅at，未返回取消收藏事件或多次收藏时间。likelist返回ids、checkPoint、code；已安装模块只传uid获取当前ID列表，没有已发现的收藏操作历史读取路径。like及like/v1是写入接口，未调用；模块中的time固定为3，不能将该参数解释为历史收藏时间。

前一轮保存的50首候选与后一次读取相比，at全部一致。本地尚没有跨越“取消—重新收藏”事件的观察，不能恢复此前已被覆盖或删除的事件。仍需账号持有人提供一首已知重新收藏过的歌及大致日期，对照当前at与首次/再次收藏日期。现有证据不足以判定at保留首次时间还是更新为最近一次加入时间。

未来连续快照只能记录观察事实：红心集合从有到无再到有表示在这些观察时点之间发生过状态变化；同一ID的at变化是时间字段变化证据，需结合状态与用户动作验证原因。两个采集时点间完整完成的取消再收藏可能被漏掉，不能称为完整操作日志。已保存的核验数据仅在本机.data中，不提交歌名、私人ID或凭证。

账号持有人随后主动取消一首歌的红心；绕过MusicMirror私有缓存读取上游likelist和红心歌单，两个来源均确认歌曲已移除，总数从309变为308，此时该歌曲at不再返回。取消前的at已保存为本机基线，取消观察另存本机文件；待用户重新点红心后比较，不预先断言时间会更新。

### 取消后重新点红心：已完成实测

同一账号、同一歌曲在用户主动重新点红心后，likelist与红心歌单均恢复该ID，总数由308恢复309；原位置与at倒序位置均为第1。at由2026-06-17 01:13:09更新为2026-09-17 17:46:22（北京时间），新at位于已记录的取消观察之后、本次读取之前。证据在本机grin-unlike-observation.json、grin-relike-observation.json，私人歌曲ID不提交。

本样本验证：该接口的at在取消后重新点红心时更新为再次加入时间，不能解释为首次红心时间。结合之前手动调序样本，可用at降序描述当前红心记录的加入顺序；不能用歌单位置代替，也不能从一条当前记录恢复历史红心次数、取消时间或全部历史。此结论已验证目标账号/部署版本上的操作，不声称所有账号或未来版本必定相同。

后续自动输入2的时间语义应为“当前红心记录最近加入时间”；近期样本可能包含以前已喜欢、后来重新点红心的作品，不可称为首次喜欢的新歌。已导出的旧快照继续保留当时未知时间，本次核验不追溯改写。自订歌单的加入时间是独立来源，尚未被此实验验证。
