# 产品指导：持续变化的音乐审美画像

所需数据、上游候选接口、实测状态与算法边界汇总见[数据需求与API能力对照](data-requirements-and-api.md)。

## 定位

传播方向采用“你的歌单，比你更了解你的音乐审美”。核心回答“长期反复听什么、最近主动喜欢什么、两者如何延续或变化”，不止展示年度排行榜。参考 [宣传稿](design/项目宣传点.md) 的隐藏偏好、画像与变化，每条解释都要能展开看到样本、因子和证据。

宣传稿中的情绪、人声、旋律、节奏、人格是创意方向，不是现有数据能证明的事实。未经验证的音乐特征不生成对应结论；不从播放结构推断心理原因或评价品味高低。

## 输入1：长期听歌结构

使用账户可见的长期 Top100、播放次数、歌曲/歌手/专辑元数据。明确范围是“接口可见长期样本”，不保证包含注册以来所有播放。

按播放次数加权，解释集中度、有效曲库、歌手/专辑深听和广度。排行榜作为证据，解读哪些作品构成长期中心、少数作品承担多少播放。曲风/语言无可靠数据时隐藏，不从歌名猜测。

## 红心与歌单操作的术语

红心/喜欢是加入“我喜欢的音乐”；将歌曲加入自订歌单是另一种主动选择，不能通过likelist验证其歌单成员状态。收藏/订阅整张歌单又是歌单级行为，不等于给其中每首歌点红心。当前输入2仅采集红心歌曲，文档旧称“收藏”特指这组红心输入，不代表已分析自订歌单。API的recent-favorites及likedAt名称保留兼容，likedAt指红心加入时间。目标账号实测取消后重新点红心会更新at，应解释为当前记录最近加入时间，而不是首次喜欢；详见[核验记录](metadata-enrichment.md)。未来自订歌单输入应独立保存playlistId、歌曲成员及加入时间来源，不混入红心状态。

## 输入2：近期红心偏好

最多50首用户明确指定的近期红心歌曲，附可选收藏时间。按每首歌曲等权，合作艺人均分歌曲权重，表示主动审美选择。

- 提供保存/读取 API 和 GUI 按钮处理器。输入2独立查询，不合并为最近播放模块。
- `/likelist` 验证当前红心状态，不假设 ID 列表顺序就是收藏时间。
- 目标账号的at已完成手动调序、取消/重新点红心实测；自动配置及正式上游时间来源契约尚未接入。当前允许用户选择并提供时间；历史未知保持 `likedAt:null`，不追溯改写成一周内或最后50首。
- 演示账号用明确标记的合成收藏。真实账号未配置返回 `not_configured`；主动清空返回 `empty`。
- 已取消红心的选定歌曲标记 `likedVerified:false`；喜欢列表不可用时是 null。保留用户输入，不伪造验证。
- 后续确认红心歌单排序和时间语义后接入自动采集，保持模块输出契约。

## 两模块对照与辅助数据

收藏模块有自己的歌手/专辑分布，另给出与长期 Top100 的歌曲交集、新歌手权重比例及歌手分布 JSD。清楚标注长期按播放加权、收藏按歌曲等权。

可解释为“选定收藏中30%出现在长期样本”“40%的收藏艺人权重来自长期样本未出现的歌手”，不能称作人生首次喜欢或永久审美改变。

最近播放、周播放是辅助输入。主结果使用12类审美卡片：反复中心、审美坐标、主动喜欢与实播、延续性、发现、关系生命周期、时间背景、选择生态、周期、流行度、声音偏好和轨迹。完整当前喜欢列表与输入2选定红心分开；旧六指数只保留在历史快照。

## GUI 动作与验收

登录/绑定 → 编辑近期收藏 → “看看我到底喜欢什么”（刷新、轮询） → 长期结构/近期收藏/对照 → 审美卡片解释 → 历史/比较/趋势 → 解绑/删除/退出。

当前实现调用层和事件处理；[独立UI设计稿](ui-design/README.md)覆盖全流程，尚未接入视觉页面。模拟链路要求两个模块可独立获取、输入2变化产生新快照、三个可比快照可查看趋势；缺失数据明确降级，所有结论附证据。
